# 0018 Password sign-in as an alternative to passkeys

**Status:** Accepted, 2026-11-09. Amends [0004](0004-passkeys.md) and [0014](0014-spa-authentication.md) ("passkeys only") and the last-passkey rule of [0017](0017-passkey-links-and-user-administration.md).

## Context
Passkeys are the main sign-in (ADR 0004), but some household members use devices or password managers without passkey support, or simply do not want one. Identity already stores a password hash, a lockout end and a failed-attempt count on every user, so a password needs no new tables. Users created so far have their internal ID as Identity's `UserName`, because a passkey needs no login name. The app is reachable only on the private network (ADR 0006), but a password can still be guessed, so guessing must be slow and must not reveal which usernames exist.

## Decision
- **Either method is enough.** A user has a passkey, a password, or both: these are their *sign-in methods*. First run and invite links let the person choose; a recovery link sets a new password or adds a passkey; My account adds the other method later. The last sign-in method cannot be removed (checked under the user administration lock of ADR 0017).
- **Username.** Password sign-in uses a *username*: unique and case-insensitive (Identity's normalized user name and its unique index), 3 to 32 letters, digits, `.`, `_` or `-`, trimmed and stored in Unicode NFC. There is no email. A user without one keeps the internal ID as `UserName` until they choose a username, which happens only together with setting a password; a username can never look like an internal ID (32 hexadecimal characters), so the two cannot collide. The rules are enforced by an Identity `IUserValidator` in place of Identity's ASCII-only character list, and checked again by the endpoints for a readable validation problem. Every change of a username runs under the user administration lock, so "unique" holds under concurrent requests.
- **Policy through Identity options.** Passwords have 12 to 128 characters with no character-type rules (NIST SP 800-63B style): `IdentityOptions.Password` sets the minimum and turns the other rules off, and an `IPasswordValidator` adds the maximum. Lockout is Identity's: 5 failed attempts lock the user out for 15 minutes; failures are counted per user and reset by a successful sign-in or a recovery link.
- **Sign-in.** `POST /api/auth/sign-in/password` (anonymous, antiforgery as in ADR 0014) runs `PasswordSignInAsync` with lockout and starts the same persistent session as a passkey. An unknown username, a user without a password, a wrong password and a locked-out user all get the same 401 problem; an unknown username still hashes the password, so the answer takes as long. Attempts against a user without a password do not count towards the lockout, so nobody can lock a passkey-only user out by guessing.
- **First run and links.** `POST /api/setup/complete-with-password` and `POST /api/passkey-links/redeem/{token}/complete-with-password` take a display name (invites only), a username and a password; they share the first-run transaction and the link rules of ADR 0017 with their passkey counterparts. A recovery link asks for a username only if the user has none. Redeeming a recovery link, with either method, ends the user's other sessions (new security stamp) and lifts a lockout.
- **My account.** `POST /api/me/password` sets a password (with a username when the user has none), `PUT` changes it given the current one, `DELETE` removes it while a passkey is left. Each changes the security stamp, so other devices sign out at their next session check, and reissues the current session. They answer with the current user. `/api/me` returns the username and the sign-in methods; the members list shows admins each user's methods.
- No new migration: the columns are Identity's.

## Consequences
- Removing the last passkey is allowed when the user has a password, and removing the password when they have a passkey.
- A known username can be locked out by anyone who can reach the sign-in screen, for 15 minutes at a time. On a private network this is acceptable; lockout also blocks passkey sign-in, as `PasskeySignInAsync` does.
- Changing the password needs only the current password, not a fresh sign-in; a fresh check for changing any sign-in method is left to PAN-27.
- Usernames are chosen once; renaming is not offered.
